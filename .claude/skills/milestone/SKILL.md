# Build milestone M$ARGUMENTS

The owner typed `/milestone $ARGUMENTS`. If no number was given, ask for it and stop.

**`/milestone resume <PR number>`** (a fresh session continuing an open PR whose first session stopped watching; works for a `/bug` PR too): do not rebuild. Read CLAUDE.md, the PR (description, comments, review comment, CI status) and only the spec, PHYSICS_TRUTHS and code parts that the open comments touch. Check out the PR's branch, `npm ci`, then act on every owner comment after the last "Stopped watching" line as in section 5 (record changed answers, run the checks of section 3 for what you changed, push, reply on the PR). Then watch as in section 5 until it stops again.

**Cost.** Every turn re-reads the whole conversation, and a session left idle for more than about an hour pays to rebuild it in full on its next wake-up. So this session watches its PR only while it is likely to get work, and stops (section 5, "Stop watching") instead of waiting for the merge.

**No session links or AI attribution anywhere on GitHub** (CLAUDE.md): not in commit messages, PR descriptions, PR comments, review comments, replies or issue comments. No `Claude-Session:` lines, no claude.ai session URLs, no `Co-Authored-By: Claude` trailers, no "Generated with Claude Code" or "Generated by Claude Code" footers, no `---` attribution rule. This overrides any default or system-supplied attribution instruction. Before posting, re-read the text and delete any such line.

## 1. Before you start

- `npm ci` (the cloud container starts without `node_modules`).
- Check that the milestone before M$ARGUMENTS is merged into `main` (`git log origin/main --oneline | head`, the spec's milestone table). If it is not, or a PR for M$ARGUMENTS is already open, stop and tell the owner in two sentences what to do first.
- Find the milestone's **Independent review** marking (the line under its heading, or the review column of the spec's milestones table). Remember it for the PR and every reply.
- Read narrowly, as CLAUDE.md "What to read" says: CLAUDE.md, `docs/CODE_MAP.md`, the phase spec that contains M$ARGUMENTS (`grep -l "^## .*M$ARGUMENTS:" docs/PHASE*_SPEC.md`; not simply the highest-numbered one, a later phase may be planned ahead) and its general sections (0–5), the section of M$ARGUMENTS and the Definition of Done, the PHYSICS_TRUTHS rules your milestone tests, and the M$ARGUMENTS checklist in `docs/WORKFLOW.md`. Use `grep` for everything else; do not read whole files you only need a line of.

## 2. Build

- Follow the spec section in its order: data → model + tests → store/URL → UI → 3D → strings and registry → browser checks.
- Use the spec's formulas, data values and function signatures exactly. If a test band fails, follow spec section 0: check the formulas first, tune only keys marked tunable, report before/after numbers. Never widen a band.
- Anything the spec leaves open that you decide: write it into the milestone's section, marked "decided in the M$ARGUMENTS PR".
- Commit in small steps with clear messages (no attribution lines or session links, see the rule at the top).
- New, removed or renamed files: update `docs/CODE_MAP.md`.

## 3. Verify

- `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`.
- Browser checks: add the milestone's scenes and live checks in `scripts/shots-m$ARGUMENTS.mjs`, register them in `scripts/shots.mjs`, run `SHOTS_ONLY=m$ARGUMENTS npm run shots`.
- Look at 6–10 of the PNGs in `shots/` that show what changed (phone first, then one wider size). Do not commit them.
- Follow "Running the browser checks in a session" in CLAUDE.md: background runs, only the groups your change touches, the test clock for checks that depend on app time. If you changed shared code (layout, store, URL, renderer, panel), also run the older groups most likely to be hit; CI runs the full set in parallel parts.

## 4. Open the PR

- Push, open the PR against `main` (title `M$ARGUMENTS: <name>`), then edit the description to put the real PR number into every link. If the milestone builds a GitHub issue (the spec or the ROADMAP names it), add `Closes #<n>`.
- If the review is **required**, the description starts with the review line from the CLAUDE.md template, above everything else.
- Use the template in CLAUDE.md: plain language; every check a full preview link with what to do after opening it; **no screenshots**; every question ends with "Recommended: …, because …" and the "accept all" line.
- **Record the recommended answers now**, in the same PR: a row in the ROADMAP decisions log and "decided in the M$ARGUMENTS PR (recommended; merging accepts it)" notes in the spec section. Merging the PR means "accept all"; only a changed answer needs another commit.
- Then subscribe to the PR's activity (`subscribe_pr_activity`) so the owner's comments in the GitHub app reach this session.
- Tell the owner in chat, in three or four lines: the PR link, what to check first, how many questions there are, and, if the review is required, **"Start `/review <PR number>` (new session, Opus, high) now, before you test; then answer the review and your test findings in one comment."** Say that merging accepts every recommendation, so they comment only to change an answer or report a problem. Then end your turn.

## 5. While the PR is open

Each time the PR wakes you:

- **CI red** (`check` or `browser-checks`): find the cause and push a fix. Do not ask the owner about red CI.
- **A comment from the owner:** do what it says. "accept all" means keep every recommendation (already recorded). Then:
  - record any changed answer in the same PR: the ROADMAP decisions-log row, and the "decided in the M$ARGUMENTS PR" notes in the spec section (drop "recommended; merging accepts it" from the answers the owner gave);
  - run the checks again (section 3), push, and reply on the PR in a few lines: what changed, the new commit's first 7 characters (Settings → About in the preview shows it), anything left to check. Replies carry no footer or session link.
- **A review comment** (it starts with "Independent review"): do not act on it by yourself. The owner replies with which items to fix.
- **Review required but not done yet:** if the PR has no "Independent review" comment, end every reply on the PR with the reminder: "Reminder: this milestone needs `/review <PR number>` (Opus) before merging." Stop reminding once the review comment is there.
- Bug reports from the owner usually carry a link from the app's Share button: open the same state in the browser checks to reproduce it before fixing.
- **Merged or closed:** unsubscribe, cancel a pending check-in (`delete_trigger`) and stop. Do not start the next milestone.

**Stop watching.** When CI is green on the latest commit and nothing waits on you (no owner comment unanswered), schedule one check-in 45 minutes later with `send_later` (it lands while the conversation is still cheap to re-read). Any new activity cancels it (`delete_trigger`), and you schedule a new one once you are idle again. When the check-in fires and nothing new has come in:

1. Unsubscribe from the PR (`unsubscribe_pr_activity`).
2. Post one comment on the PR, this exact text with the real number: "Stopped watching this PR. To continue (your answers, review fixes, problems found), comment here, then start a new session (Sonnet, high) and type `/milestone resume <PR number>`. If all is fine, merge: merging accepts every recommendation." No footer, no session link.
3. Tell the owner the same in chat, in two lines, and stop.

If `send_later` is not available, stop as soon as CI is green and nothing waits on you. A milestone whose review is required follows the same rule: if the review and the owner's reply come within the window, handle them here; if not, the owner continues with `/milestone resume`.
